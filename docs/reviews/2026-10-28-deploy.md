## Summary
1. HIGH: `do_rollback()` accepts any int, including negative — verified `steps_back=-1` silently re-uploads the **oldest** retained snapshot to the live FTP site (`deploy/rollback.py:176-199`); `deploy.sh --rollback=-1` passes it straight through.
2. HIGH: `list_releases()` sorts every directory under `deploy/releases/` by name without filtering to the `NNNNNN-` sequence pattern — verified a stray dir (e.g. `backup`) sorts to `releases[0]`, is shown as "(live)", and shifts every rollback index (`rollback.py:99-107`).
3. MEDIUM: `send_file()` puts FTP credentials on the curl command line (`--user "${FTP_USER}:${FTP_PASS}"`, `deploy.sh:85`), visible to any local user via `ps`; and the snapshot taken before upload is treated as "live" even when the upload later fails, so a rollback after a failed deploy re-publishes the version that is already live instead of going back one.

## Bugs

- **HIGH — `deploy/rollback.py:176-188` (`do_rollback`): no lower bound on `steps_back`.**
  `if len(releases) <= steps_back:` only guards the upper end. Verified in a scratch run: with 3 releases, `do_rollback(steps_back=-1)` uploads `releases[-1]` — the **oldest** snapshot — to the live host, and `steps_back=0` re-uploads the current one. `main()` (`rollback.py:340`) parses `int(sys.argv[2])` with no validation, and `deploy.sh:44` (`--rollback=*`) forwards the value unfiltered, so `bash deploy/deploy.sh public --rollback=-1` publishes the oldest retained site.
  Fix: at the top of `do_rollback`, `if steps_back < 1: raise RollbackError(f'steps_back must be >= 1, got {steps_back}')`. (Same one-liner applies to `do_local_rollback`, `rollback.py:289`, where a negative value flips `current` forward.)

- **MEDIUM — `deploy/rollback.py:107` (`list_releases`): stray directories under `RELEASES_DIR` become releases.**
  `return sorted((d for d in RELEASES_DIR.iterdir() if d.is_dir()), reverse=True)` accepts any dir; `_next_sequence()` (l.116-117) filters with `_SEQ_RE` but `list_releases` does not. Verified: dropping a dir named `backup` into `deploy/releases/` makes it `releases[0]`, printed as `(live)` by `main()` (l.338), and shifts every real release's index by one, so the default rollback re-uploads a backup dir's contents and `steps_back=1` no longer means "the previous deploy".
  Fix: filter like `_next_sequence` does — `if d.is_dir() and _SEQ_RE.match(d.name)`.

- **MEDIUM — `deploy/deploy.sh:85` (`send_file`): FTP password on the command line.**
  `curl -s -T "$local_path" "$remote_url" --user "${FTP_USER}:${FTP_PASS}"` — the full password is visible in `ps`/`/proc/<pid>/cmdline` to every user on the machine for the whole upload. Fix: pass credentials out-of-band, e.g. `curl --netrc-file <(umask 077; printf 'machine %s login %s password %s\n' "$FTP_HOST" "$FTP_USER" "$FTP_PASS")` or write a temp netrc and `curl -K -` with the config on stdin.

- **MEDIUM — `deploy/deploy.sh:110` + `rollback.py:176-188`: a failed deploy's snapshot is counted as "live", so the next rollback is off by one.**
  deploy.sh runs `rollback.py snapshot` *before* any upload (per the module docstring, l.6-8, and `list_releases`'s assumption "releases[0] is what's live right now", `rollback.py:16-17`). If any `send_file` then fails (exit 1, l.90), the never-uploaded snapshot stays `releases[0]`. A subsequent `rollback` (steps_back=1) re-uploads `releases[1]` — which is the version actually still live — so the operator sees "Rolled back" while nothing changes, and must know to pass `2`.
  Fix: have `snapshot_release` create the dir with a `.pending` suffix (or a `PENDING` marker file) and have deploy.sh/deploy.ps1 clear the marker only after the last successful `send_file`; `list_releases()`/indexes then skip pending dirs.

- **MEDIUM — `deploy/rollback.py:159-173` (`_ftp_upload_all`): `ftp.quit()` in `finally` can mask the real error.**
  `finally: ftp.quit()` — if `login()` or `storbinary()` already raised (bad credentials, disk full mid-STOR), the server often closes the connection, `quit()` then raises `EOFError`/`error_perm`, and that secondary exception replaces the actionable first one.
  Fix: `finally:\n    try: ftp.quit()\n    except Exception: pass`.

- **MEDIUM — `deploy/deploy.sh:60-65` (env parsing): a CRLF `.env` keeps `\r` in values, unlike the Python parser.**
  `declare "${BASH_REMATCH[1]}=${BASH_REMATCH[2]}"` captures `FTP_PASS=p4ss\r` verbatim, so logins fail with an invisible trailing character — while `web/utils.py load_env()` (used by rollback.py) calls `.strip()` and strips the `\r`. The two readers of the same file therefore disagree. The repo targets Windows too (deploy.ps1), so CRLF `.env` files are likely.
  Fix: `v="${BASH_REMATCH[2]}"; declare "${BASH_REMATCH[1]}=${v%$'\r'}"`.

- **MEDIUM — `deploy/rollback.py:256-286` (`publish_local`): re-publishing an existing version merges into the old release dir.**
  `release_dir.mkdir(parents=True, exist_ok=True)` (l.269) then copies files in; files present in the old release but absent from the new file set (a removed image, a deleted locale) survive and are served under the "new" release — and if `current` already points at that version, they are served live mid-publish.
  Fix: build into `release_dir.with_name(version + '.tmp')`, then `shutil.rmtree(release_dir)` + `os.replace()` before flipping `current`.

- **LOW — `deploy/rollback.py:121-143` (`snapshot_release`): a snapshot copy interrupted mid-way is kept as a valid release.**
  Each file is copied with `dest.write_bytes(...)` (l.138) directly into the live-named dir; an interrupt (Ctrl-C, full disk) leaves a partial release that later becomes a plausible rollback target. Fix: copy into `f'{release_dir.name}.tmp'` and `os.replace()` into place at the end.

- **LOW — `deploy/deploy.sh:133` : unset `LOGO_PNG` (or `FTP_HOST`/`FTP_DIR`/`FTP_USER`/`FTP_PASS`) crashes with a raw `unbound variable`** (from `set -u`) *after* export and snapshot have already run. Fix: after the env-file parse, loop over the required keys and exit with a named error, e.g. `for k in FTP_HOST FTP_USER FTP_PASS FTP_DIR LOGO_PNG; do [[ -n ${!k:-} ]] || { echo "Missing $k in $ENV_FILE" >&2; exit 1; }; done`. (Verified by reading; the exact crash text is bash's, not observed in a run.)

- **LOW — `deploy/rollback.py:340,369` (`main`): non-numeric N raises an uncaught `ValueError` traceback** instead of the friendly `Error: …` used everywhere else (`rollback local 2x` → traceback). Fix: wrap the `int()` in try/except and `sys.exit` with a message.

Verified non-issues (checked, not reported as findings): the `declare` env parse does not re-evaluate values, so `$(...)` in `.env` is not command-injected; the `[[ -d … ]] && cp` and `curl && return` failing-AND-lists under `set -e` do not abort the script (both reproduced in scratch bash runs — `build.sh:15`, `deploy.sh:86`); timestamps use `timezone.utc` throughout; rollback upload paths are built from snapshot-relative names only, no user input, so FTP path traversal is not reachable in normal use. FTP itself is plaintext-by-design per the README ("curl … for FTP upload") — flagged as an improvement, not a bug.

## Implementation gaps

- **`deploy/build.sh:3-4` vs `deploy/rollback.py:64-93` — the "same file set" claim is false for `health.json`.** build.sh says dist/ is "the exact tree … (same file set as deploy/rollback.py _release_files())", but build.sh writes `dist/health.json` (l.20-30) and `_release_files()` has no health.json entry. Consequences: (a) `rollback.py rollback` never restores `health.json`, so after a rollback the live site reports the version/last_update of the *newer* build it rolled back from — exactly the field the home-lab update check reads; (b) `deploy.sh:120-125` uploads `dist/health.json` whenever it exists, and nothing in the `deploy.sh public` path ever regenerates it (only build.sh does), so a stale health.json from an old build is silently re-uploaded on every plain deploy. Fix: add `health.json` (from `dist/`, if present) to `_release_files()`, and/or have deploy.sh skip the upload when `dist/health.json` is older than `web/index.html`.

- **`deploy/rollback.py:256` (`publish_local`): no validation of `version`.** The docstring ties the release name to the VERSION file (via `_version()`, l.210-213), but nothing checks it against `_VERSION_RE`. A malformed `VERSION` (e.g. `1.2`, or `1.2.3-beta`) creates a release dir that `_version_key` sorts as `(-1,-1,-1)`: it is the first thing pruned and can never be picked as a rollback target — a silent failure mode. Fix: in `publish_local`, `if not _VERSION_RE.match(version): raise RollbackError(f'VERSION {version!r} is not X.Y.Z')`.

- **`deploy/rollback.py:121-143` (`snapshot_release`): empty snapshots are accepted**, in direct contrast to `publish_local`, which deliberately refuses them ("refuse to flip onto an empty release", l.258-279). Verified: `snapshot_release({})` creates a valid-looking release that becomes `releases[0]` / "(live)" and shifts rollback indexes (though `do_rollback` itself later raises on an *empty target*). Fix: mirror publish_local — raise `RollbackError` when `files` is empty.

- **`deploy/deploy.sh:141,151,175`: unguarded globs.** With `nullglob` unset, `I18N_FILES=("$WEB_DIR/i18n"/*.json)` (and the data/labels globs) keep the literal pattern when no file matches, so the deploy dies after 3 pointless curl retries + `sleep`s on a path like `/…/i18n/*.json` with a misleading "Upload failed after 3 attempts". Fix: `shopt -s nullglob` near the top (l.18). For `IMAGE_FILES` (l.162) also skip non-files (`[[ -f $f ]] || continue`) — unverified whether export.py can produce subdirectories under `web/images/`.

- **`deploy/rollback.py:159-164` (`_ftp_upload_all`): missing env keys surface as a raw `KeyError`.** `env['FTP_HOST']` etc. with no check; `do_rollback()` called from CLI with a `.env` missing `FTP_PASS` prints a traceback, not the actionable "set FTP_PASS in .env" the README implies. Fix: validate the three keys and raise `RollbackError` naming the missing one.

- No `TODO`/`FIXME` markers exist in any of the five reviewed files (checked with grep). `tests/helpers.py` `create_fixture_db` is not used by `test_rollback.py` (it serves the export/labels tests) — that is fine, not a gap.

## Improvement suggestions

1. `rollback.py:_ftp_upload_all` — wrap `ftp.quit()` in try/except (Bug #5); one-line change, removes the worst traceback-masking in the rollback path.
2. `deploy.sh:85` — move credentials off the command line into a temp netrc (`curl --netrc-file`); removes the only local credential leak.
3. `rollback.py:_flip_current:249` — use a unique temp name (e.g. `current.tmp.{os.getpid()}`) instead of the shared `current.tmp`, so two concurrent publish/rollback invocations cannot clobber each other's symlink between `symlink_to` and `replace`.
4. `rollback.py:110-118` — `_next_sequence()` + `snapshot_release()` have a TOCTOU between reading the max seq and `mkdir`; `release_dir.mkdir(parents=True, exist_ok=False)` in a retry loop (catching `FileExistsError`, incrementing seq) closes it for free.
5. `build.sh:26` — `pathlib.Path('VERSION').read_text()` has no explicit `encoding`; on the Windows path (deploy.ps1 exists, so Windows is a real platform here) this uses the locale codec. Add `encoding='utf-8'` to match `_version()` in rollback.py.
6. `rollback.py:162` — `ftplib.FTP(host)` is plaintext, including the login. If the host ever supports FTPES, `FTP_TLS` is a drop-in one-line hardening; README already commits to plain FTP, so this is optional.
